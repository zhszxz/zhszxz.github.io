一、RAG 的两种实现方式

前面两篇拆解了 RAG 的各个环节，实际落地有两种组织方式：

  1. 手动拼接：自己写「检索 → 拼提示词 → 调模型」的代码（第 6 篇 2.3 已示范）。简单直接，但检索时机固定。
  2. Agentic RAG（智能体 RAG）：把「检索」封装成工具交给 Agent，让模型自己决定什么时候检索、检索什么。更灵活，是生产主流。

本篇重点讲 Agentic RAG，以及你项目里完整的生产级流水线。

2.2 Agentic RAG 的妙处

  • 模型自主决策：模型判断「这个问题需要查资料吗？」→ 需要就调 retrieve_docs 工具，不需要就直接回答。检索不再是固定步骤。
  • 工具描述引导检索：@tool 的 docstring 告诉模型「什么时候该用这个工具」，system_prompt 进一步约束「必须基于文档、不得编造」。
  • 可扩展：可以再加「查询数据库」「调外部 API」等其他工具，模型会在多种工具间自主选择。

对比手动拼接，Agentic RAG 把「要不要检索、检索什么」的决策权交给了模型，是更智能的形态。

3.5 步骤 ④：父子块切分（Parent-Child Chunking）

这是高级切分策略——两级切分：

为什么父子块？

  • 子块（child chunk）：小块，向量化后精确检索，召回最相关的片段。
  • 父块（parent chunk）：大块，上下文完整，作为最终喂给模型的上下文。

检索时「命中子块 → 返回其父块」，既保证了检索精度，又保证了上下文的完整性，避免「只给模型一句孤零零的片段」。

四、完整流水线小结

把整条链路串起来，一张图看懂生产级 RAG：

关键设计：

  1. LLM 文档清洗：解析后的脏 Markdown 用 LLM 规范化，是检索质量的前提。
  2. 父子块切分：检索用小块（准），回答用大块（全），是生产 RAG 的重要优化。
  3. 混合检索 + 向量库：Milvus 存稠密（语义）+ 稀疏（关键词）双向量，混合检索召回。
  4. 向量库 + 关系库分工：Milvus 管向量检索，PostgreSQL 管父块原文和业务数据。

小结

本篇是 RAG 系列的收官，把前面所有环节串成可落地的方案：

  1. Agentic RAG：把「检索」封装成 @tool 交给 Agent，让模型自主决定何时检索，比手动拼接更智能。
  2. 生产级流水线 6 步：查询 → 解析 → LLM 优化 → 父子块切分 → 双库入库 → 检索。
  3. 两个关键技巧：LLM 清洗文档、父子块（Parent-Child）切分，是提升检索质量与回答质量的核心。
